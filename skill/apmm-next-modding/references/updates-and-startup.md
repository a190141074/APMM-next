# 更新交接、启动与增量核查

适用于覆盖更新、重启未响应、扫描缓存和启动性能任务。先读当前工程 `docs/UPDATING.md`、`docs/ARCHITECTURE.md`，以下记录的是决策边界；具体参数和命令以当前源码为准。

## 更新与重启不是同一条安装事务

| 安装身份 | 程序与数据位置 | 保留的更新边界 |
|---|---|---|
| portable | 解压目录；旁置 data | 发行清单与 `portable_update::ALLOWED` 的共同白名单；备份、整批替换、新版就绪、失败恢复 |
| MSI | 安装目录；LocalAppData/APMM | Windows Installer 事务；普通权限观察与重启、提权进程仅安装 |
| legacy-bridge | 已公开的旧版原目录和 data | 旧二进制固定白名单；新版核验后交接 next 助手 |
| compat-0.3.39 | 本地测试版原目录和 data | 独立旧 runner 兼容包；不能与公开旧版桥接混用 |

- 身份来自当前副本的 `installation.json`，缺失标记按已有便携兼容规则处理。不能发现另一份 MSI 安装就改变当前便携副本的数据落点。
- schema 2 清单必须唯一匹配平台与安装身份；schema 1 旧入口提供旧客户端能处理的桥接包。不能找不到匹配项就取第一个资产。
- 下载收据、大小、SHA-256、发行文件和版本核验成功后，关闭新写入入口并等待已登记任务清空。独立助手报告准备就绪后主窗口才退出；不能启动助手后立即强杀主程序。
- 便携助手等待旧 PID 真正退出。新版启动成功由工作区初始化确认，进程存在不是就绪证据；失败恢复白名单文件，未知用户文件、data、Vault 不参与替换。
- MSI 提权取消时保留原窗口。安装进程清空 `AUTOLAUNCHAPP`、`WIXUI_EXITDIALOGOPTIONALCHECKBOX`，不能填 `0`：旧模板按非空判断，仍会自动启动。由普通权限观察进程启动新版，避免提权应用误写数据。
- Installer 返回成功后仍核对安装身份、版本及发行文件。MSI 不套用便携文件回滚；卸载不附带用户数据清理。
- 保留 `data/updates`、独立 staging 的安装日志、就绪和一次性结果记录。失败重试前读记录，不能靠删除整个 data 或共用缓存处理更新故障。

定位：`installation.rs`、`update_channel.rs`、`update_package.rs`、`update_install.rs`、`update_gate.rs`、`portable_update.rs`、`msi_update.rs`、`update_bootstrap.rs`、`bin/astral-updater.rs`。

## 覆盖更新的验收层级

- `tools/verify-updater.mjs` 使用合成的旧版/新版可执行文件直接测便携助手，覆盖替换成功、启动失败回滚和中断恢复；它不覆盖应用内下载、安装交接或真实 MSI 安装。
- `tools/verify-update-app.mjs` 启动发行版并通过真实 IPC 执行便携更新。默认夹具从本轮 payload 复制当前版本；跨版本验收需设置 `APMM_UPDATE_BASE_ZIP` 为已核验的较早发行包，再从报告核对 `fromVersion` 与目标版本。独立桌面启动器须在旧程序退出后保持桌面，直到脚本关闭输入管道，让更新助手能在同一桌面启动新版。
- `tools/verify-msi.ps1` 的管理展开只检查 MSI 内容，不注册或覆盖产品。覆盖升级、UAC 取消和卸载行为需要独立 Windows 安装验收；包展开结果不能代替这些证据。
- 分开记录助手事务完成、安装后的文件/身份核验和新版工作区启动确认。任一层通过都不能代替其余层。

## 先确认真实未响应原因

1. 从实际 EXE 路径、版本、运行日志与用户触发步骤开始。Windows“未响应”需看窗口消息响应，不能仅由页面白屏或动画猜测。
2. 用用户现有库的独立副本复现，并核对候选数、槽位、应用状态和监听设置。空库测试曾遗漏 806 个候选下的启动阻塞。
3. 分开测窗口线程执行、库锁等待、目录观察、哈希、PNG 解码、快照生成与页面渲染。`spawn_blocking` 解决窗口线程执行位置，不能证明重复工作或长持锁已解决。
4. 对照既有索引和事务：曾因逐游戏文件复制并排序整库放大同步耗时；修改查找方式时仍要保留同摘要不同槽位、候选独立资料、禁用状态和回滚语义。

测试默认使用已验证的独立 Windows desktop 启动器，显式指定 `APMM_BACKGROUND_LAUNCHER` 与 `APMM_TEST_PYTHON`。缺少启动器先核对配置，不能回退成弹窗打扰用户。用户明确要求可见预览时，在 Codex 打开回环地址；这与后台原生验收分别处理。

## 缓存与扫描的修改前自检

- `Library` 是权威状态；展示快照与文件校验缓存都可重建。有效展示快照的只读返回不能等待后台重建锁，否则仍会拖慢首屏。
- 文件缓存关联实际目录、文件标识、大小、高精度修改时间、摘要及校验规则/格式版本。只复用成功校验；坏缓存重建，缓存写入失败不撤销已经提交的库事务。
- 元数据匹配只用于快速筛选；保留手动“扫描本地”的强制完整校验，以及应用到游戏前的内容校验。保持全部文件元数据的外部改写不能宣称由快速模式完全发现。
- 强制校验失败先撤销旧的成功缓存，库中候选记录继续保留；否则下次启动会再次信任已判坏的结果。读取失败不等于删除。
- 枚举、读取、哈希和解码在工作线程及库锁外观察；短提交阶段复核库版本、扫描代次、文件状态和枚举后新增项，冲突重新排队，不能覆盖扫描期间的新编辑或应用。
- Vault 与游戏目录复用同轮观察结果，但保留各自提交语义；自身事务事件不能引起重复扫描循环。
- 文件通知合并后检查具体路径；溢出、失效和目录替换时重建监听并完整核对。Windows 旧句柄可能继续监听已改名目录，不能只看线程是否存活。退出、切目录时取消并释放句柄。
- 页面增量携带前后 revision；拒绝迟到结果，断档补取完整快照。保留滚动、选择、候选路径和归属；无变化核对不重复触发整库刷新。

定位：`file_verification.rs`、`directory_observation.rs`、`directory_scan.rs`、`directory_watch.rs`、`directory_monitor.rs`、`workspace_cache.rs`、`original_cache.rs`、`vault_sync.rs`、`directory_sync.rs`、`core/domain/workspace.ts`。

## 计时与最终包验收

- “启动到列表”从 Windows 原生进程创建时间开始，到目标资源列表实际可见；`performance.now()` 只覆盖 WebView 生命周期，曾把实际 3.85 秒误报为 2.8 秒达标。
- 分别记录首次建缓存、连续三次无变化暖启动、关闭期间文件变化；后台 PNG 内容读取/解码与按需预览读取独立统计。窗口响应探测与扫描耗时也分别报告。
- 验收必须读取当前 VERSION，并核对本轮构建报告、源码输入摘要与实际 EXE；另一聊天推进版本时保留其改动，完成当前源码对应的构建。用户未要求历史复现时，不自行冻结旧版本作最终交付。
- Codex 预览打开前核对端口占用者的命令行和返回的页面标题。参考项目与 APMM Next 可以同时运行；端口被占用时为当轮预览指定空闲回环端口，并给验收脚本传同一 URL。启动前将浏览器 profile、临时目录和发行输出显式设在 B 盘，避免缺省写入系统盘。
- 等任务结果前核对真实终态：当前成功状态为 `completed`，不是 `success`。超时先查任务日志与测试断言，不能直接认定应用卡死。
- 本次相关回归覆盖同大小改图、恢复时间戳、重命名、同摘要不同槽位、坏图与坏缓存、目录移走/替换、扫描中编辑/应用/取消/退出。并核对候选资料、应用状态、预设和原安装/游戏摘要。
- 入口：Rust `incremental_tests`、原有同步过滤测试、前端 `core/domain/workspace.test.ts`；正式包用 `tools/verify-incremental-native.mjs`，其任务路径仍需显式设置 `APMM_INCREMENTAL_WORK`，不要沿用旧默认目录。启动器须提供原生进程创建时间和窗口响应采样。

历史证据仅用于定位：2026-11-15 的 0.4.6 隔离验收记录三次暖启动约 1.42 秒，首次约 5.94 秒；1325 次窗口探测最大 4 ms，无变化后台 PNG 重读与解码均为 0。它不为后续 0.4.7 或新修改自动背书。旧报告归档可从 `B:\APMM-next-work\repository-cleanup-20261115` 查找，实际日志和报告存在性必须重新核对。
